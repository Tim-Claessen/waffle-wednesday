# Decisions taken during the build

[PLAN.md](../PLAN.md) is the authority on what is being built and why. This file records
what was decided while building it — the places where an implementation detail turned out
to have a real consequence, and the two places where the plan was wrong.

---

## Decided from research, not a probe

### The video provider: R2, with a remux in the browser

Phase 0 was meant to settle this by recording on an iPhone and an Android. There was no
iPhone to hand, so it was settled from published browser support instead (September 2026).

| | iPhone (Safari) | Android (Chrome) |
| --- | --- | --- |
| Records H.264 + AAC in MP4 | Yes, since iOS 14.5. Until 18.3 it was the *only* format | Yes, since Chrome 126 (June 2024), using the phone's H.264 encoder |
| Plays the other's file | Yes | Yes. H.264 MP4 is the one format every phone decodes |
| The catch | The MP4 is **fragmented**, with a zero duration in its header | Same |

The codec question came out the way R2 needed. The catch is new: both browsers write
fragmented MP4 whose `mvhd` duration is zero. A browser then has to download much of the
file before it knows the length or can seek, other players don't show a length at all,
and [media.ts](../src/lib/media.ts) reads the zero as a real duration, so the card would
say 0:00.

The fix is a **remux, not a re-encode**: rewrite the same H.264 and AAC samples into an
ordinary MP4 with the index at the front and a real duration. It takes about a second on
the phone, before upload, using [Mediabunny](https://mediabunny.dev). No quality loss, no
server work, and the Worker still receives a file it can probe properly.

Why not Bunny Stream: it would fix this too, and it would accept iPhone camera-roll HEVC.
But the camera-roll path already gets a rejection that points at the recorder, and a
dependency in the browser is cheaper than a second vendor with its own dashboard, key and
bill for a problem one library solves. If the camera-roll rejection proves a real nuisance
once people use it, that's the moment to revisit. [storage.ts](../src/lib/storage.ts)
still keeps the swap to one file.

Checked on the laptop with a real Chrome 153 recording of three minutes: the original
came out as 54 fragments with no readable length; the remux gave one index, a length of
179.98 seconds, the same codecs, and took 0.4 seconds. Both pass the upload barrier.

What stays unverified until it's tried: an actual iPhone recording played on an actual
Android and back. That gets done on a rented real iPhone before anyone is invited
([setup.md](setup.md#the-iphone-check-without-an-iphone)), never by asking a friend to
test.

Sources: [WebKit's MediaRecorder notes](https://webkit.org/blog/11353/mediarecorder-api/),
[Chrome's intent to ship MP4 in MediaRecorder](https://groups.google.com/a/chromium.org/g/blink-dev/c/p1OMVj1FrMI),
[addpipe on duration in Chrome and Safari MP4s](https://blog.addpipe.com/duration-in-mp4-files-produced-by-chrome-safari/),
[Mediabunny's conversion guide](https://mediabunny.dev/guide/converting-media-files).

## Decided while building

### Cloudflare Workers, not Pages

PLAN.md says Cloudflare Pages. The build deploys as a **Worker with static assets**
instead.

Pages Functions cannot have cron triggers. Since the reminders are the thing that makes
this a ritual rather than a video folder, and PLAN.md says never to cut them, a hosting
choice that can't schedule anything is the wrong one. Workers with static assets gives the
same server-rendered Astro output, the same free tier, the same custom domain, and bindings
and scheduling as first-class features.

This is also just where Cloudflare has moved: `astro add cloudflare` generates a
`wrangler.jsonc` with a `main` and an `assets` directory, with no Pages option offered.

### A separate cron worker

Even on Workers, the app's entry point is generated by `@astrojs/cloudflare` and resolves a
Vite virtual module at build time. There is no supported way to add a `scheduled()` handler
to it.

So [workers/reminders](../workers/reminders) is a second Worker whose entire job is to make
one authenticated HTTP request to `/api/cron/reminders` on a schedule. The reminder logic
stays in the app beside the templates and queries it uses, and it can be triggered by hand
with `curl` — which is the only sane way to test a Wednesday-morning email on a Tuesday
afternoon.

### Reminders run every thirty minutes, not at two fixed times

PLAN.md specifies two cron lines: `30 23 * * 2` and `0 12 * * 3`, being 07:30 and 20:00
Perth.

But PLAN.md also puts the reminder times in the `groups` table, explicitly "so it changes
without a deploy". Both cannot be true: with hard-coded cron lines, changing a reminder time
on the settings screen would do nothing at all, and the screen would be lying.

So the cron fires every thirty minutes and the app decides whether anything is due, using
each group's own reminder time and timezone. Forty-eight invocations a day of a Worker that
almost always decides "nothing" is free, and the settings screen is honest.

The consequence: reminder times land on the half hour. `07:30` and `20:00` both do already.

Because each thirty-minute slot is visited exactly once, a configured time matches exactly
once per week, so this stays idempotent without a table of sent reminders — which would
have been a seventh table for a nine-person app.

### Everything is a server round trip, and the video is too

There is no client-side data fetching and no JSON API for the feed. Pages are rendered on
the server, where the session lives.

Video is served through `/api/video/{waffleId}` rather than from a provider URL. The route
looks the waffle up, the policies decide whether the caller may see it, and only then are
any bytes read. Three consequences worth knowing:

- Provider portability stops being an aspiration. No template can hold a provider URL,
  because none of them holds a URL at all.
- An asset id on its own is worthless. Leaking one doesn't leak a video.
- Range requests have to be handled by hand, which
  [assets.ts](../src/lib/assets.ts) does, because iOS Safari will not play a video it
  cannot seek in. Without the 206 path the player shows a black frame and nothing else.

### The upload barrier reads the file, not the form

PLAN.md says duration is "probed for duration before upload and re-checked against the
stored metadata after". With R2 there is no provider metadata to re-check against, so the
server reads duration and codec out of the file's own bytes: enough of ISO base media
format and EBML to find an `mvhd` and an `stsd`, and nothing more. It's about 200 lines in
[media.ts](../src/lib/media.ts), and it's tested against synthetic files including the
moov-at-the-end layout an iPhone produces.

One honest limitation: a WebM written live by `MediaRecorder` usually carries no duration
at all. When the container has none, the server falls back to what the client declared, and
if there is no declaration either it accepts the file — at which point the recorder's own
hard stop at 3:00 is the only control left. Bunny would close this gap by reporting a real
duration after ingest.

### Known risk: a 50 MB upload is buffered whole in the Worker

`/api/waffles` reads the entire file into memory so the probe can walk it, then writes it
to R2. At the 20 MB target this is comfortable. At the 50 MB cap it is not obviously safe —
a Worker isolate has a bounded memory budget, and `formData()` plus `arrayBuffer()` holds
the file twice.

This is untested and should be tested deliberately in Phase 1: pick a file just under 50 MB
from a camera roll and post it. If it falls over, the fixes in order of preference are

1. lower the cap — 50 MB only ever catches camera-roll picks anyway, and the message
   already steers those to the recorder;
2. probe from a bounded head of the file and accept a weaker duration check on `.mov`,
   where `moov` sits at the end;
3. upload straight to R2 with a presigned URL and probe asynchronously afterwards, which is
   a larger change and reintroduces an `uploading` state that currently never occurs.

The in-app recording path, which is the one everybody will actually use, is nowhere near
this limit.

### Six tables, and no table of who hasn't posted

The schema is exactly the six from PLAN.md. There is no seventh table, and more
importantly there is no query anywhere that returns the members of a group who haven't
posted.

[reminders.ts](../src/lib/reminders.ts) computes that set once, to address an envelope, and
throws it away on the next line. It isn't returned, isn't logged by name, and no page can
reach it. `eveningReminder()` takes no parameter that could carry it, so there is no
version of that email that mentions anybody else — the constraint is in the function
signature rather than in a reviewer's memory.

### Rows are `type`, not `interface`

In [database.types.ts](../src/lib/database.types.ts). Supabase constrains a schema to
`Record<string, unknown>`, and TypeScript gives an implicit index signature to a type alias
but never to an interface. Declaring the rows as interfaces makes every query in the app
silently resolve to `never` — it type-checks as long as you never touch a property, and
then fails everywhere at once.

### Accounts come from invites, never from the login form

Supabase's public sign-ups are off, and the "send me a sign-in link" button passes
`shouldCreateUser: false` ([login.astro](../src/pages/login.astro)), so typing an unknown
address there sends nothing and creates nothing. Either one alone leaves a gap: the
setting stops the API, the flag stops the form.

Tim wants friends to join with no dashboard work. That doesn't need sign-ups on: the Phase 2
invite link creates accounts on the server with the service key, which the setting doesn't
restrict. The design is in [PLAN.md](../PLAN.md#phase-2-joining-without-the-supabase-dashboard).

### Its own Supabase project

The free plan allows two active projects per person, and both were taken. Sharing one with
another app was ruled out because Auth is per project: the other app's "any signed-in user"
policies would have covered this group's accounts too. Instead yumlog moved into wrapt's
project (2026-09), which freed a slot. Waffle Wednesday holds other people's videos and
accounts, so it's the one that gets a project to itself.

## Where the design files disagree with PLAN.md

`design/claude_code_implementation_prd_design_tokens.md` is a generated PRD that came back
with the screen designs. Its **visual** direction — Hearth & Table, the peat and ember
palette, EB Garamond over Manrope — is what got built, and the tokens are now in
[global.css](../src/styles/global.css).

Its engineering half contradicts PLAN.md in five places, and PLAN.md won each time, per
CLAUDE.md. Recorded here so it doesn't get re-litigated:

| The PRD says | What was built | Why |
| --- | --- | --- |
| Next.js 14, App Router | Astro on Cloudflare | PLAN.md's stack table, and the existing pattern |
| Magic link only, no passwords | Email and password, magic link as recovery | PLAN.md: nine people signing in twice a year shouldn't need their inbox each time |
| `video_url text not null` | `provider` + `provider_asset_id` | A stored URL makes changing provider a rebuild. This is a golden rule |
| Circles and dispatches | Groups and waffles | PLAN.md's vocabulary, and the group's own |
| "4 of 7", empty seats, muted unrecorded members, an evening digest naming who posted | None of it | **This is the shame mechanic the whole product exists to avoid.** See below |

That last row is worth being blunt about, because the design system describes an "Empty
Chair (Pending Member)" component in detail — a recessed seat with a monogram and
*"Seat reserved for [Name] — kettle's on."*

It's a lovely piece of design and it is exactly what PLAN.md forbids: an empty slot with
somebody's name in it, rendering a person's quiet week as a visible gap. It was not built.
The feed's round-table row iterates over waffles, not over members, so there is no branch
that could draw an absent person and no data available to write one with.

For the same reason the header says "Week 42" rather than "Week 42 · 4 of 7": a denominator
is a count of who's missing, wearing a hat.

The evening email keeps its *tone* and drops its content: no digest of who posted, and it
offers watching as an equal option rather than a consolation.
